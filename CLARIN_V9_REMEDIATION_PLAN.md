# CLARIN-DSpace v9 — Remediation Plan (to genuinely finish the upgrade)

> Generated 2026-07-08 by a multi-agent planning workflow (9 domain planners -> adversarial critics -> revision -> synthesis -> final evaluator; 29 agents), grounded in the 2026-07-08 adversarial audit (8 auditors + verifiers, 57 agents) of BE PR #1339 / FE PR #1316.
> **Prime directive: REUSE, don't rewrite.** Every work item names the exact `origin/dtq-dev` source to port and the v9 adaptation. Machine-checkable acceptance criteria live in `CLARIN_V9_ACCEPTANCE_CRITERIA.md`.
> Push targets: **only** BE PR #1339 (`ufal/clarin-dspace-upgrade-v9`) and FE PR #1316. No new branches/PRs.

## Executive summary

The CLARIN->DSpace 9 upgrade is NOT done: PRs #1339/#1316 are green but core CLARIN features are broken or entirely absent on the live stack, and the progress file falsely claims end-to-end success. The live re-baseline changes the shape of the work in one decisive way: the C1 item-file-listing REST tier already exists and returns HTTP 200 on :18080, but as SIX UNTRACKED working-tree files — so the very first action is to COMMIT them under a concurrency guard, not port from scratch. Overwhelmingly this remediation is REUSE, not rewrite: for nearly every gap the fix exists byte-identical (or as a small delta) in origin/dtq-dev and needs only a mechanical v9 adaptation — jakarta.* imports, the NAME->PLURAL_NAME REST bean-resolution fix (the same class of bug behind M2/M3/BE-CHK-5), registering models in provide-core models[], or hand-reconciling ~3 heavily-drifted modified-vanilla files (ItemUtils, XOAI, MetadataValidation) that will not patch cleanly. The plan is sequenced so foundations that unblock compilation and fresh-deploy correctness land first (config include for clarin-dspace.cfg, registries, and the shared DCInput.ComplexDefinitions primitive that OAI depends on), then the three security/UX criticals C1/C2/C3, then the OAI/CMDI/BibTeX export layer (C5) plus submission workflow, then the FE GUIs/facets/static pages (C4, M1-M8), then the deferred test/CI/Docker port (M11) and native-v9 adoption plus an honest progress-file rewrite. Acceptance is machine-checkable throughout: because the production assetstore is not imported, every LIVE check is a negative gate (401/403) or metadata-only 200 that short-circuits before file read, and positive byte delivery is proven only by the ported ITs that stand up their own test assetstore. All work pushes only to BE #1339 and FE #1316; no new branches or PRs.

## Final evaluator verdict on this plan

**Verdict: plan-has-gaps** — the gaps found are folded into this document as addendum work items **GAP-1..GAP-5** (see Addendum) and as acceptance-criteria hardening rules; with them applied the evaluator's objections are addressed.

The plan is unusually thorough and its claims are grounded, not vibes. I cross-checked every audit finding against a work item and against the live repos. Coverage of the criticals and majors is real: every C1-C5 and M1-M13 maps to concrete work items with dtq-dev source paths, and the mediums (submission steps S2-S7, autocomplete/metadatavalues 404, ISO facet, license-selector, ORCID bean, type-bind, Czech i18n, curation, CLI, ~120 tests) and the documented-deferred/env-gated set (assetstore/S3 sync, Shibboleth/WAYF, Matomo PDF e2e, ItemVersionLinker CLI) are all named and flagged. S3 direct download is no longer in that set: owner decision O-12 (2026-09-14) cancelled the O1 deferral and the feature is implemented on the v9 base on AWS SDK v2. I verified three things a skeptic would suspect were missing and found them handled: (a) the 6 C1 metadata-bitstream files are genuinely untracked (git status '??'), exactly as BE-BASE-0 assumes; (b) CLARIN Flyway migrations (V7.2 Lindat_Clarin_schema, V7.6 Clarin_token, Matomo_report_registry, Preview_Tables) ARE present at HEAD, so DB schema is NOT an unowned gap; (c) the dspace-oai delta is ~25 classes (HEAD 96 vs dtq-dev 121), consistent with BE-OAI-1's '28 classes'. The DoD gates (a)-(f) are objective and the sequencing (BE-BASE-0 first, DCInput.ComplexDefinitions before OAI, oai import before ListMetadataFormats verify, M13 config before downstream props) is sound. It is NOT plan-complete because a few genuine holes remain that could let the exact green-but-broken failure mode recur: an under-specified C2 (the ClarinBitstreamServiceImpl port is not named though it is absent at HEAD and the token subsystem has no positive acceptance check), a systemic verification ceiling where most live ACs are negative gates that also pass under total breakage, and thin/unowned spots (FE preview viewer component, fresh-deploy Solr configset). These are under-specification and verification gaps rather than whole-missing features, so plan-has-gaps rather than plan-inadequate.

## Cross-cutting risks

- Concurrency/clobber: the C1 tier and other fixes live as untracked working-tree files while a parallel process (container 'Up 12 minutes') edits the same area; every commit must git-diff and stage explicit paths only, re-checking git status immediately before commit, never git add -A.
- Env-gated verification ceiling: the production assetstore is not imported, so positive byte delivery (200 + content) for /content, /handle/, allzip, and populated preview fileInfo cannot be proven live — only via ITs that stand up their own test assetstore. Every live AC is deliberately a negative gate (401/403) or a metadata-only 200 that short-circuits before file read.
- Bean-resolution gotcha (NAME->PLURAL_NAME): the same bug class that left M2/M3 broken will silently 404 BE-CHK-5 and any REST repo/link ported verbatim from dtq-dev; grep-level ACs must assert PLURAL_NAME and provide-core models[] registration.
- Modified-vanilla hand-reconcile: ItemUtils (~99 lines), XOAI (~72 lines), MetadataValidation, and AuthorizeServiceImpl carry heavy v9 drift — fork patches will NOT apply cleanly and must be reconciled onto the HEAD 5-arg overloads/methods, not blindly copied (fork used English.plural / 4-arg overloads that no longer match).
- Config placement (M13): CLARIN props loaded only via gitignored local.cfg vanish on fresh clone; Matomo tracking keys must live in git-tracked modules/matomo.cfg (not clarin-dspace.cfg, whose matomo.* keys are 'no longer read'), while the CLARIN report engine reads lr.statistics.api.* from clarin-dspace.cfg — mixing these breaks both subsystems independently.
- Push restriction: only BE #1339 / FE #1316 — no new branches/PRs; all commits must target the existing ufal/clarin-dspace-upgrade-v9 branches.
- Fixture fragility: only one gated (faf919b4, confirmation=1) and one open (f15230ca, confirmation=0) UUID are pinned on the dev-5 dataset; a data refresh changes them, so self-seeded ITs are the durable proof and curl probes only a fast smoke test.
- Matomo e2e and Docker/CI depend on the deferred M11 port; without dtq-dev docker/matomo-w-db.yml only unit-level wiring can be proven, and adopting native tracking accepts the loss of OAI-PMH harvest statistics (no native OAI tracker), which interacts with C5.

### GAP-5 — OAI-PMH harvest statistics decision (medium)

Native org.dspace.matomo has no OAI tracker; dtq-dev ClarinMatomoOAITracker was dropped. DECIDE with maintainer: accept the loss (document in progress file) or re-port the OAI tracker onto the native pipeline. Until decided, list under documented-deferred with reason.

### Acceptance-criteria hardening rules (apply to the whole catalog)

- Dataset-pinned checks (specific UUIDs/handles/counts from the dev-5 dump) MUST state the dataset assumption; where possible replace with invariant checks (e.g. totalElements > 0, 'the item's own uploaded file appears').
- Every negative gate (401/403) MUST be paired with a positive check on an open resource, so over-blocking cannot pass.
- 'Renders and functions' style criteria are forbidden — each step needs a named test, HTTP probe, or exact UI assertion.
- Static-files AC must enumerate: count of files served == count of files in src/static-files/ (not a single-page sample).
- ACs gated on deferred infra (assetstore, Matomo stack, external IdP) must say so explicitly and name the IT that covers them instead.
